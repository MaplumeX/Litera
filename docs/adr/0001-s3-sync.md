# Sync via user-configured S3-compatible storage, unencrypted

Litera needs multi-device sync (library, reading positions, annotations, assistant sessions, and EPUB files), but the project has no server and its privacy promise says "books stay on your machine." We decided sync is opt-in, targets an S3-compatible bucket the user configures (custom endpoint/region/path-style, so R2/B2/MinIO work), stores data in plaintext (no client-side encryption; the README promise is rewritten accordingly and the first-enable UI states it), and runs entirely client-side — Litera operates no backend.

## Consequences

- Layout: one `manifest.json` object holds all small data (book metadata, positions, annotations, tombstones, per-item timestamps and device ids); EPUB files and covers are separate objects referenced by revision. Merge is a single GET plus in-memory union — annotations merge by id, positions take the newest `updated_at` (explicit timestamps, never file mtime; ties broken by device id), branched sessions keep both branches.
- Concurrency: manifest uploads use conditional PUT (`If-Match` etag); on mismatch, re-GET, re-merge, retry a bounded number of times.
- Deletions propagate via tombstones kept 30 days in the manifest; the local trash never syncs. A tombstone is not absolute: a book whose own revision timestamp (`bookUpdatedAt`) is newer than the tombstone is a **revival** (the reader restored it from the local trash), and the tombstone is discarded instead of the book.
- A book carries an explicit `bookUpdatedAt` recording the last edit to the record itself — metadata, curation, restore — and never a reading-position or annotation write. It orders metadata merges (so a metadata edit cannot lose to an unrelated page turn on another device) and drives the revival comparison above. Manifests written before this field existed fall back to position/annotation activity, so older data keeps merging as it did; a downgraded client may drop the field on its next upload.
- Credentials (S3 access key/secret, like existing LLM API keys) stay in local JSON files and never sync.
- New devices pull the manifest immediately (shelf renders instantly) and download EPUBs on demand; book cards show an "not cached" state. First sync on a device shows an upload-size estimate before bulk-uploading existing books.
