# Sync via user-configured S3-compatible storage, unencrypted

Litera needs multi-device sync (library, reading positions, annotations, assistant sessions, and EPUB files), but the project has no server and its privacy promise says "books stay on your machine." We decided sync is opt-in, targets an S3-compatible bucket the user configures (custom endpoint/region/path-style, so R2/B2/MinIO work), stores data in plaintext (no client-side encryption; the README promise is rewritten accordingly and the first-enable UI states it), and runs entirely client-side — Litera operates no backend.

## Consequences

- Layout: one `manifest.json` object holds all small data (book metadata, positions, annotations, tombstones, per-item timestamps and device ids); EPUB files and covers are separate objects referenced by revision. Merge is a single GET plus in-memory union — annotations merge by id (copies of one annotation ordered by its `updatedAt`, else `createdAt`; two annotations on the same CFI collapse to one), positions take the newest `updated_at` (explicit timestamps, never file mtime; ties broken by device id), branched sessions keep both branches. Every tie resolves by comparing content, so both merge orders agree.
- A position's timestamp records when it last *moved*: opening a book, or re-reporting the position it opened at, never bumps it, so a stale device cannot outrank real progress elsewhere. The app also pushes pending changes (with a short timeout) when its window closes.
- Book ids derive from the EPUB's content, so the same book imported on two devices is one book to Sync. Re-importing from the same source path still overwrites in place (tracked by a per-record source key); books imported before this keep their path-derived ids.
- Concurrency: manifest uploads use conditional PUT (`If-Match` etag); on mismatch, re-GET, re-merge, retry a bounded number of times.
- Backends without conditional PUT (Backblaze B2 answers `If-Match` with 501 Not Implemented) fall back to comparing the etag with a HEAD just before a plain PUT. This narrows the race between two devices uploading at once but cannot close it; on such a backend a near-simultaneous sync can still drop one device's manifest changes until that device syncs again.
- Deletions propagate via tombstones kept 30 days in the manifest; the local trash never syncs. A tombstone is not absolute: a book whose own revision timestamp (`bookUpdatedAt`) is newer than the tombstone is a **revival** (the reader restored it from the local trash), and the tombstone is discarded instead of the book.
- A book carries an explicit `bookUpdatedAt` recording the last edit to the record itself — import, metadata, curation, restore — and never a reading-position or annotation write. It orders metadata merges (so a metadata edit cannot lose to an unrelated page turn on another device) and drives the revival comparison above. Manifests written before this field existed fall back to position/annotation activity, so older data keeps merging as it did; a downgraded client may drop the field on its next upload.
- Credentials (S3 access key/secret, like existing LLM API keys) stay in local JSON files and never sync.
- App preferences (theme, UI language, typography) never sync: desktop and phone are different interfaces and want different settings. The Manifest still has a `preferences` envelope for older clients; newer clients never apply it and pass it through unchanged, so older clients keep converging among themselves.
- LLM provider configuration (provider choice, model, thinking level, custom endpoints) never syncs either: a provider setup belongs to the machine that runs it — localhost endpoints and per-device keys differ — and API keys already never sync. The Manifest still has a `provider` envelope for older clients; newer clients never apply it and pass it through unchanged, so older clients keep converging among themselves.
- New devices pull the manifest immediately (shelf renders instantly) and download EPUBs on demand; book cards show an "not cached" state. First sync on a device shows an upload-size estimate before bulk-uploading existing books.
- A device that receives a newer file revision for a book it already holds (re-imported elsewhere) does not push its older file back; it downloads the newer one the next time the book is opened.
- What a device remembers about the Sync Backend's objects (uploaded file and session revisions, the bulk-upload confirmation) is reset when the endpoint, region, or bucket changes, so the new backend receives everything.
