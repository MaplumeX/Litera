# UI i18n

> How Litera translates React chrome. Book text, AI replies, and Rust/runtime error originals are not translated.

---

## Design Decision: in-house catalogs, not preferences.json

**Context**: The UI needed `zh-CN` / `en` with an immediate switch and a persisted choice.

**Options considered**:
1. i18next + React Context
2. Store `locale` on `preferences.json` next to theme
3. In-house `t()` + `localStorage` + a module store

**Decision**: Option 3.

- Two locales and `{name}` interpolation do not justify i18next.
- Frontend spec forbids Redux / Zustand / React Context. Locale is a module store; components subscribe with `useSyncExternalStore` (`useT()`). Non-React code calls `t()` directly.
- `PreferencesDataRaw` uses `deny_unknown_fields`. Adding `locale` would make older builds treat the file as corrupt and reset theme/typography. Persist to `localStorage` key `litera.locale` only.

**Do not** add `locale` to `src-tauri/src/preferences.rs` or `save_preferences`.

## Signatures

```ts
type AppLocale = "zh-CN" | "en";

detectLocale(languages?: readonly string[]): AppLocale
initLocale(): AppLocale          // call from main.tsx before render
getLocale(): AppLocale
setLocale(locale: AppLocale): void
t(key: MessageKey, vars?: Record<string, string | number>): string
useT(): { locale: AppLocale; t: typeof t; setLocale: typeof setLocale }
```

Storage: `localStorage["litera.locale"]` is exactly `zh-CN` or `en`. Anything else is ignored.

Unset → `detectLocale()`: first `navigator.languages` / `navigator.language` tag whose primary subtag is `zh` → `zh-CN`, else `en`. Then persist the resolved value.

`setLocale` / `initLocale` set `document.documentElement.lang`.

`t()` replaces `{name}` only. Missing key returns the key and `console.warn` in DEV.

Catalogs: `src/locales/zh-CN.ts` and `src/locales/en.ts` must export the same `MessageKey` set (`src/lib/i18n.test.ts` asserts key parity).

## Convention: UI chrome uses `t()` / `useT()`

**What**: User-visible React strings (labels, dialogs, empty states, aria-labels, frontend-built prefixes such as `导入失败：`) live in the catalogs.

**Why**: Hardcoded Chinese cannot switch. Backend `{message}` stays English inside a translated wrapper.

**Example**:
```tsx
const { t, locale, setLocale } = useT();
t("library.importFailed", { message });
```

Language names in Settings → Appearance stay native (中文 / English) and are not catalog keys.

`useT()` must run before any early return. Conditional hook calls break when the skip condition flips (`PersistenceErrorBanner`).

Non-React code (`agent-reducer`) calls `t("chat.newSessionTitle")` at event time. Already-stored session titles are not rewritten when the locale changes. Rust session-summary fallback remains `"新会话"` and is outside UI i18n scope.

## Tests

- Vitest `setupFiles` (`src/test/setup-i18n.ts`) pins `zh-CN` before render. jsdom `navigator.language` is usually `en-US` and would fail existing Chinese queries.
- `src/lib/i18n.test.ts`: OS detect, persist, interpolation, missing key, catalog key parity.
- At least one component test switches to `en` and asserts an English string.
- Existing Chinese role/text queries stay valid under the zh-CN default.

## Wrong vs Correct

#### Wrong
```ts
// preferences.rs — old builds deny_unknown_fields and reset the file
locale: Option<String>,
```

```tsx
if (!message) return null;
const { t } = useT(); // hook after conditional return
```

#### Correct
```ts
setLocale("en"); // localStorage + document.lang + subscribers
```

```tsx
const { t } = useT();
if (!message) return null;
```
